## Context

Some logical keys are stored as structures of primitive vectors even though their complete equality identity is an
ordered fixed-width tuple. A long decimal is one example, but the same physical fact can hold for UUID-like values,
timestamps with zones, intervals, and provider-defined records. Nitro's exact structural key kernels preserved
correctness for those values, but invoked provider semantic operations row by row and prevented the grouping, join,
and distinct consumers from using the generated primitive table shared under ADR-0036.

The q85 prototype replaced one structural key with its provider-known primitive tuple. Against the established
35.714-second Cork control, Cork+Nitro fell from the prior structural path to 28.668 seconds, with 0.800x CPU and
0.771x allocated bytes relative to control. The improvement came from changing the calling convention and generated
loop shape, not from decimal-specific arithmetic or an engine-owned i128 type.

## Decision

A type provider may publish a `FixedWidthKeyLayout` proving that non-null logical key identity is exactly raw equality
of one ordered tuple of primitive lanes. Each lane declares an `I32`, `I64`, `F64`, or `BOOLEAN` carrier and an
immutable path of structural field names; an empty path selects the logical value itself. Field names and tuple
partitioning are physical access metadata and assign no logical meaning in Nitro. In particular, a provider may
describe two limbs of an i128 value without Nitro treating either limb as independently meaningful.

The complete logical value owns nullness. Every selected structural component must be non-null when its enclosing
logical value is non-null. `F64` key identity uses raw bits because the provider's layout declaration is an exact raw
identity proof, not a request for floating-point comparison semantics.

At batch binding, Nitro resolves flat, region, dictionary, nested-dictionary, and RLE wrappers into exact primitive
arrays, offsets, and row mappings. Generated grouping, distinct, and join kernels cast those arrays once and perform
carrier-specific primitive loads, hashing, exact probing, and null handling directly in their row loops. They do not
invoke method handles, `VectorAccess` value interfaces, provider virtual methods, or row-wise structural objects in
those loops. Grouping retains logical representatives for output, distinct retains its requested SQL null behavior,
and joins retain build multiplicity and skip null keys; these consumer semantics remain outside the shared table.

Carrier/vector mismatch, nullable selected components, unsupported wrapper representations, and unsupported lane
counts reject the declared capability loudly. Nitro does not route an incompatible declared layout through the
row-wise semantic implementation after admitting the fixed-width path. A type that does not publish the proof keeps
its exact semantic key implementation.

## Consequences

- One provider declaration supplies the same exact primitive identity to grouping, distinct, and joins.
- Hot fixed-width loops are monomorphic generated bytecode with direct array and mapping loads.
- Adding a carrier or wrapper extends one binder and generator rather than one implementation per logical type or
  consumer.
- Providers remain responsible for logical identity and for deciding whether a physical decomposition is exact.
- Exact dynamic-filter publication for composite provider layouts is not part of this decision. Such joins retain the
  existing structural-key behavior: they use the generated build/probe index but do not separately collect primitive
  component filters whose conjunction would not, by itself, express tuple membership.
- This decision neither introduces an i128 carrier nor selects interleaved versus split storage. Those remain separate
  physical-layout investigations.
- Cross-consumer tests cover flat and encoded inputs, sparse masks, SQL null modes, duplicate joins, and prepared join
  probe views. Incompatible declarations have explicit rejection tests.

## Alternatives considered

**Use row-wise semantic method handles as a compatibility bridge.** Exact, but leaves polymorphic invocation and
provider dispatch in the dominant loop and makes an admitted Nitro path predictably slower than its intended design.

**Recognize long decimals or two-long structures in operators.** Rejected because the engine would infer logical
meaning from a physical shape and every new composite type would require another special case.

**Add an engine-owned i128 carrier first.** Potentially useful for later arithmetic and storage work, but unnecessary
for a provider-neutral arbitrary-lane key contract and insufficient for other structured fixed-width values.

**Materialize one canonical scalar or interleaved vector before each key consumer.** Makes the table simple but adds
another row-proportional pass and forces one storage policy on providers and connectors.
