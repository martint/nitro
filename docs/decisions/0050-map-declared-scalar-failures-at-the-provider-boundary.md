# ADR-0050: Map declared scalar failures at the provider boundary

- **Status:** accepted
- **Date:** 2026-09-03
- **Spec:** §6, §8
- **Depends on:** [ADR-0008](0008-use-first-class-masks-and-streams.md), [ADR-0013](0013-use-layered-function-calling-conventions.md), [ADR-0049](0049-exclude-invalid-rows-from-fallible-scalars.md)

## Context

A generated scalar loop can invoke a registry-resolved host target, but an exception from one selected row formerly
aborted the batch. Conditional SQL needs declared function failures to remain row-local until the enclosing mask
decides whether they are observable. Nitro cannot identify provider exception classes or assign provider error codes,
and catching failures around carrier access or output allocation would misclassify infrastructure defects as data.

## Decision

Allow the provider to attach a `ScalarFailureMapper` to an exact scalar target. Generated bytecode catches `Throwable`
only across the target invocation. The mapper returns a classloader-neutral `ErrorValue` for a declared row failure
and rethrows everything else. The adapter records mapped failures in the requested ERRORS vector and continues the
batch. Input errors are propagated before invocation and prevent the target from observing their unspecified values.
Carrier readers and result writers execute outside the protected region.

The failure path may dispatch through a provider interface because it is exceptional; the successful generated loop
retains the constant `invokedynamic` target and no per-row classification branch beyond the exception table. If no
mapper is supplied, target failures propagate exactly as before. A mapper attached to a target declared infallible
is ignored, so the generated hot loop has no exception table for a failure mode excluded by its resolved semantics.

## Consequences

- Conditional evaluation can suppress a declared failure from an inactive branch without aborting the batch.
- Nitro remains independent of host exception classes and error catalogs.
- A mapper cannot hide cancellation, VM errors, or linkage problems unless a provider violates the contract;
  allocation and writer defects are outside the protected region entirely.
- ERRORS-only demand invokes a fallible target but merely propagates inputs through an infallible target.
- Native batch implementations remain appropriate when successful-path error detection is cheaper without exceptions.

## Alternatives considered

**Catch every runtime exception as a row failure.** This hides engine and provider defects and assigns no stable error
identity.

**Teach Nitro about Trino exceptions.** This breaks classloader neutrality and makes the engine depend on a host.

**Protect the entire generated row body.** This incorrectly turns carrier-reader, allocator, and result-writer bugs
into SQL data errors.

**Always abort the batch.** This cannot implement conditional error isolation for scalar-adapted functions.
