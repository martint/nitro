## Context

ADR-0089 lets a provider prove that raw equality of an ordered primitive-lane tuple is logical key identity. Some
fixed-width logical keys have a stable primitive representation but require canonicalization before raw equality is
valid. ClickBench q42 groups a short timestamp with time zone: packed zone bits are representation metadata and must
not participate in instant identity. Canonical floating-point identity and multi-field temporal normalizations have
the same shape even though their logical types and source carriers differ.

Pre-materializing one canonical vector would add a row-proportional pass and storage policy. Invoking a provider
method handle through a general row loop would restore the performance bridge rejected by ADR-0090. Adding one table
or generator for each logical type, source-carrier combination, or canonical result shape would create a
combinatorial implementation matrix and move provider semantics into the engine.

## Decision

A provider-declared fixed-width key lane may be either one raw primitive source or one canonical 64-bit lane projected
from any positive number of supported primitive sources. Every source independently declares its carrier and
structural field path. A projection is an exact provider-owned method handle whose primitive parameters exactly match
the ordered sources and whose result is `long`. Providers may declare multiple lanes when canonical identity needs
more than 64 bits. Source paths, lane partitioning, and canonical bits remain physical metadata with no logical
meaning in Nitro.

Nitro resolves all source vectors and wrapper mappings once per batch. The fixed-width table generator consumes one
exact physical layout descriptor containing the source carrier sequence, source count per canonical lane, and
projection identities. It generates source loads, mapping traversal, canonical projections, hashing, probing, and
insertion as one loop. Projection targets are held as hidden-class data and linked into generated bytecode through a
constant `invokedynamic` call site. The hot loop does not use `MethodHandle.invoke`, virtual provider dispatch,
`VectorAccess` interfaces, row objects, or a projection pre-pass.

The general abstraction is a fixed-width key table and layout, not a multi-long or logical-type table. Raw tuples,
mixed primitive sources, and projected structures all use the same descriptor and generator. The table currently
normalizes each canonical lane into 64-bit storage; that is a physical table representation rather than an engine
claim about the logical type. Adding a new primitive carrier extends the descriptor binder and generator switches
once. It does not add carrier-combination interfaces or logical-type-specific table classes.

The enclosing logical key owns nullness. Every selected component must remain non-null for a non-null enclosing value.
An incompatible source, nullable selected component, unsupported wrapper, invalid projection signature, or excessive
canonical lane count rejects the capability before table mutation. It never enters a semantic object-table fallback.

## Consequences

- Canonical timestamp, floating-point, temporal, and provider-defined identities can share grouping, distinct, hash
  join, and membership kernels without engine type recognition.
- Exact generated shapes include projection target identity as well as carriers, lane partitioning, mappings, and
  table-storage policy.
- The generated loop may contain a constant-linked projection call, but not megamorphic or per-row method-handle
  dispatch.
- Providers own normalization and must prove that the complete projected tuple exactly identifies logical keys.
- Variable-width and recursive structural identities remain separate coverage gaps until they receive their own
  provider-neutral generated physical layouts.

## Alternatives considered

**Add timestamp-with-zone and floating-point special cases to the table.** This would close the immediate queries but
would make every new provider type another engine change and eventually require a matrix of table implementations.

**Generate a class for each named logical type.** Static dispatch would be fast, but logical type identity would enter
the engine cache key and generator boundary. Exact physical layouts already contain every property that changes code.

**Pre-materialize canonical vectors.** This offers simple table code and may be useful as an independently measured
producer capability, but it adds a complete pass and allocator-owned storage before every persistent key consumer.

**Invoke a generic projection interface or method handle per row.** This avoids materialization but preserves virtual
or polymorphic dispatch in the dominant loop and repeats the correctness-first bridge rejected by ADR-0090.
