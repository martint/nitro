# ADR-0055: Link generated aggregation targets as constants

- **Status:** accepted
- **Date:** 2026-09-03
- **Spec:** §8, §12.1, §16
- **Depends on:** [ADR-0006](0006-keep-logical-semantics-in-registries.md), [ADR-0012](0012-execute-over-encoded-domains.md), [ADR-0015](0015-keep-aggregate-state-with-function-providers.md), [ADR-0037](0037-link-generated-scalar-targets-as-constants.md), [ADR-0054](0054-generate-fixed-width-structural-projections.md)

## Context

Generated grouped aggregation originally invoked state through carrier-specific engine interfaces such as
`LongStateUpdate` and `DoubleStateUpdate`. Extending that pattern to composite or mixed-carrier states would create an
interface for each signature and would make provider state types conform to engine-owned implementation shapes.

A generic method-handle loop avoided those interfaces, but an instance-field handle did not reliably inline through
the hot row loop. Generated scalar adaptation had already established that exact handles can remain classloader-neutral
and optimizable when linked as constants.

Encoded-domain aggregation adds a second requirement. A logical contribution repeated many times may sometimes be
combined algebraically, but only the function provider knows whether and how that is valid.

## Decision

Each provider-authored grouped update carries an exact method handle whose arguments are opaque provider state, group
id, and one primitive contribution. The generated hidden class receives descriptors as class data and links each
handle through an `invokedynamic` constant call site. Generated bytecode does not symbolically reference the provider
state class.

[ADR-0056](0056-allow-generated-aggregation-updates-to-consume-tuples.md) subsequently generalizes the contribution
from one primitive value to an ordered primitive tuple while retaining this decision's constant-linking, cache-key,
and provider-owned repetition rules.

The provider may also expose an exact repeated-update handle accepting the logical multiplicity. If absent, the engine
invokes the ordinary update for every occurrence. The engine does not infer algebraic properties from a function name
or state representation.

Target identity participates in the generated-kernel cache key. Two functions with identical physical contribution
shapes cannot accidentally share a kernel linked to the first function's target.

## Consequences

- One contract supports opaque, composite, and mixed-carrier state without a combinatorial interface hierarchy.
- Hot generated loops retain constant-linked exact calls that HotSpot can optimize.
- Encoded-domain speedups remain provider-declared and semantically safe.
- Providers that omit repeated semantics remain correct, with cost proportional to logical multiplicity.
- State binding uses opaque objects and occurs only after allocation or growth.

Engine Coverage q187 validates a mixed double-and-long geometric-mean state over one billion logical rows backed by a
sixteen-value encoded domain. With the repeated target, warmed Nitro execution used about 0.607 CPU-seconds and 87.8 MB
allocated, versus 6.031 CPU-seconds and 8.22 GB for the unchanged Cork control. The point of this evidence is the
general encoded-domain and mixed-state contract, not a function-specific engine optimization.

## Alternatives considered

**Add interfaces for every carrier and state combination.** Direct calls are simple, but the API grows
combinatorially and exposes provider implementation shape in the engine.

**Store method handles in generated-kernel instance fields.** Classloader-neutral, but prior measurement showed that
the JVM did not optimize cheap row updates reliably through mutable instance-held handles.

**Let the engine multiply repeated contributions.** Valid for some sums and counts, invalid for general functions.
Only the provider can declare a correct repeated update.

**Cache solely by physical contribution shape.** Smaller cache, but incorrect because the linked function target is a
constant property of the generated class.
