# Scan-vs-compute split: Nitro compiled vs Velox — all TPC-H / TPC-DS / ClickBench

**Date:** 2026-06-17. Each engine's time is split into Parquet **scan/decode** vs downstream **compute** (joins, group-by, aggregation, sort). Nitro: JMH compiled total × measured scan fraction (`CompiledQuerySupport.ScanProfile`). Velox: clean sweep total × per-operator scan/compute fraction (`OperatorWall` task stats). ClickBench is the 822 MB subset. compute-ratio = Nitro compute ÷ Velox compute (<1 = Nitro compute faster). Caveat: on dynamic-filter queries Velox's compute runs on post-filter rows while Nitro's runs on all rows, so a high compute-ratio there reflects row count, not kernel speed.

## Overall

- geomean total Nitro/Velox = **1.15×** over 131 queries
- geomean compute Nitro/Velox = **0.60×**  (90/131 Nitro-compute-faster)
- median scan Nitro/Velox = **1.66×**

**Takeaway:** across the full suite Nitro is markedly **scan-bound** (median ~75–80% of time in Parquet decode vs Velox's ~30–65%), and Nitro's **compute kernel is faster than Velox's** on the large majority of queries. The Velox gap is therefore overwhelmingly the **scan/decode path** (Nitro decode ~1.5× slower per unit AND a larger share). The exceptions are the dynamic-filter outliers (e.g. q88/q64/q23) where Velox's pushed-down filter shrinks its compute input — there Nitro's all-rows compute looks slower, but that is the filtering effect, not the kernel. Investment priority: **scan/decode (SIMD decode + dynamic filtering)**; the compute engine is already ahead of Velox.
